WHERE I’M USEFUL

Tell me where it gets ugly.

You don’t need the feature list first. Give me the part that stopped being simple.

01“It works until people do it twice.”+

Payment retries. Duplicate submissions. Two tabs. Back-navigation. Reopening the app.

When one intention can become two requests, I look for identity and idempotency before I add another disabled button.
02“Nobody knows which number is actually true.”+

The UI says one thing. Cache says something older. Database says something else.

That is an authority problem before it is a rendering problem.
03“It works at your desk.”+

Then Chrome gets backgrounded on an Android phone, the connection changes, and the user returns twenty minutes later.

I treat resume, stale state, weak networks and small screens as product states — not surprises.
04“We’ve fixed this bug before.”+

If the same bug keeps returning in different clothes, I assume the implementation is obeying the wrong rule somewhere.

I trace the rule — state ownership, timing, cache, database or API — and fix that instead of the latest symptom.

NexTrade / case study

NEXTRADE / 01

The interface can explain the state. It cannot define it.

A financial system gets dangerous when presentation quietly becomes authority.

01THE SITUATION

A balance can look right while being wrong.

Client state can be stale, a request can commit while its response disappears, and a user can retry because the interface gave no useful answer. Treating the displayed number as financial truth makes all of those ordinary failures expensive.

02THE RULE

Put financial truth behind the interface.

Spot and Vault state are derived from authoritative ledger/database rules. Trading resolves execution authority server-side. Retryable financial actions carry stable identities so the same intention does not become two actions because the network behaved badly.

03WHAT THAT FORCED ME TO CHANGE
  • Separate presentation readiness from financial authority.
  • Preserve warm workspace state while authoritative balances revalidate.
  • Distinguish cached, stale, refreshing, rate-limited and unavailable market states.
  • Keep execution price outside browser authority.
  • Encode architectural constraints in repository-owned release audits.
04WHERE IT BROKE

The useful bugs were rarely where they first appeared.

Market timeframes reset, returning sessions blanked, image loading raced, and generic feedback repeated. Fixing those exposed deeper rules about async identity, attention, cache provenance and warm-state restoration.

05WHAT I KNOW NOW
Cached state can preserve the experience. It cannot inherit the authority of the ledger.

QuickShop / case study

QUICKSHOP / 02

The network became a synchronization target, not a prerequisite.

Useful business work should not vanish because connectivity does.

01THE SITUATION

Small-business software meets bad networks quickly.

Inventory work, sales and catalogue updates happen on phones in conditions where connectivity can be weak, interrupted or simply unavailable.

02THE RULE

Persist the intention before waiting for the network.

Pending actions live locally in IndexedDB and reconcile against Supabase when connectivity returns. The service worker and sync layer have separate jobs instead of pretending “offline” is one feature.

03WHAT THAT FORCED ME TO CHANGE
  • Design local persistence and pending synchronization explicitly.
  • Handle stale caches and service-worker upgrades instead of hiding them.
  • Keep inventory, reporting, vendor catalogue and WhatsApp ordering coherent across different product surfaces.
  • Treat mobile interaction and low-cost Android behavior as first-class constraints.
04WHERE IT BROKE

A loading skeleton that never leaves is still a data bug.

Chrome and Opera behaved differently under stale service-worker state, exposing how easily cache strategy can masquerade as a rendering problem.

05WHAT I KNOW NOW
Offline-first is not “make a cache.” It is deciding what can stay useful while synchronization is impossible.

Obsidian / case study

OBSIDIAN / 03

Store the content. Minimise the trust.

Encryption is more interesting when it changes what the backend is allowed to know.

01THE SITUATION

“Protected on the server” still means the server can usually read it.

For private notes and files, I wanted the storage layer to hold useful data without automatically inheriting the ability to decrypt the content.

02THE RULE

Encrypt before synchronization.

The browser uses the Web Crypto API, AES-GCM and a derived key so note/file contents become ciphertext before reaching Supabase. The active decryption key remains client-controlled.

03WHAT THAT FORCED ME TO CHANGE
  • Make encryption part of the data model, not a badge in the UI.
  • Keep the master key outside backend storage.
  • Treat lock/unlock state as a real application boundary.
  • Be precise about what is protected: content is encrypted, while authentication and limited metadata still exist outside that ciphertext.
04WHERE THE IDEA STOPS

Zero knowledge is a threat-model claim, not a vibe.

Client-side encryption reduces what the backend can learn from stored content, but frontend integrity and metadata still matter. The project is stronger when those limits are explicit.

05WHAT I KNOW NOW
Privacy is often less about adding protection everywhere than about removing knowledge from places that never needed it.
